# feature-store

Feature Store powering `IFeatureStoreAdapter` (offline features for training,
online features for inference). Uses Feast — **works right away, locally**,
no extra service in `docker-compose.yml` needed: registry and online store
are both local SQLite files, offline store is a local Parquet file.

`adapters/ai_platform/feature_store_adapter.py` (`FeastAdapter`) defaults to
`FEAST_REPO_PATH=infra/feature-store` — no env var needed for local dev.

## First time (build the registry + online store)

```bash
cd infra/feature-store
../../.venv/bin/feast apply
../../.venv/bin/feast materialize 2020-01-01T00:00:00 2030-01-01T00:00:00
```

`data/registry.db` and `data/online_store.db` are generated by these
commands (gitignored) — re-run them after editing `feature_definitions.py`
or `data/transaction_features.parquet`.

## What's defined here

One entity (`entity`, joined on the `entity_id` column — `FeastAdapter`
hardcodes that column name in its `entity_df`/`entity_rows`, so any new
feature view must key on it the same way) and one feature view,
`transaction_features` (`amount`, `merchant_category`, `hour_of_day`),
sourced from `data/transaction_features.parquet` — the same rows as
`data/classification-telco-fraud-detection/telco-fraud-detection-sample.csv` (Golden Path #1's fraud-detection sample),
with `transaction_id` renamed to `entity_id` and a synthetic
`event_timestamp` added (Feast requires one for point-in-time joins) since
the training sample doesn't carry one.

## Wired into Golden Path #1

`POST /datasets/enrich-features` (`services/orchestration-api/routers/models.py`)
merges Feast features into a dataset before training — called by the
`orchestration:enrich-dataset-features` Scaffolder Action, itself an
opt-in step (`useFeast` parameter) in `templates/train-track-register/template.yaml`
(frontend repo, `cuongct924/AI-delivery-portal-frontend`).
Most runs leave `useFeast` off and are unaffected.

## Pointing at real Object Storage

`feature_definitions.py`'s `FileSource` reads `FEAST_OFFLINE_STORE_PATH`/
`FEAST_S3_ENDPOINT_URL` (see `.env.example`) — unset (or blank) falls back
to the local demo parquet above. To connect to real data instead:

1. Set `FEAST_OFFLINE_STORE_PATH=s3://<bucket>/<path>/features.parquet` and
   `FEAST_S3_ENDPOINT_URL=<object-storage-endpoint>` — same
   `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` DVC already uses (Feast goes
   through the same boto3/s3fs credential chain).
2. If the real dataset's identifier column isn't literally named
   `entity_id`, add `field_mapping={"<real_column>": "entity_id"}` to the
   `FileSource` — **never** rename it in `FeastAdapter` itself.
3. `registry`/`online_store` in `feature_store.yaml` stay local SQLite —
   only the offline `FileSource` needs to change for training-time
   connectivity. A production online store (Redis/DynamoDB) for serving-time
   lookups, and a Helm chart, are not implemented yet — this repo is scoped
   to local dev + real-offline-data-connectivity only, same as
   `infra/vector-dbs/README.md`'s note on Qdrant's Helm chart.
