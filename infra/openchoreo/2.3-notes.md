# Phase 2, sub-step 2.3 — findings (not implemented)

Scoping notes from checking this sub-step's 3 pieces against the actual
cluster/repo state, before writing anything. Nothing here is applied.

## Keycloak → Thunder: the real migration list is empty

`infra/keycloak/realm-export.json` only ever defined the realm
(`ai-delivery-portal`) and 1 OAuth client (`golden-paths-agent`, used for
MCP server-to-server auth) — **no `users`, `groups`, or `roles` blocks at
all** (confirmed by loading the JSON and checking those 3 top-level keys).
The Phase 2 plan's mục 6.2 worried about losing human user access on
cutover; there's no human user list to lose here — this local dev realm
was never populated with one. The only thing that actually needs a Thunder
equivalent is the `golden-paths-agent` OAuth client registration, the same
way Thunder's own bootstrap already registers `openchoreo-backstage-client`
(`configmap/thunder-bootstrap`'s `51-backstage-app.sh`, found earlier this
session). That's a small, concrete task — not the open-ended "list every
real user" risk the plan assumed.

Still not done: actually registering that client in Thunder and re-pointing
`services/orchestration-api/auth/keycloak.py` at it. Left for a dedicated
pass since it touches live auth for whichever golden-paths-agent caller
depends on it.

## InferenceService ComponentType: blocked on KServe not being installed

`kubectl get crds` on `openchoreo-quick-start` returns zero
`serving.kserve.io` resources — KServe was never installed on this
cluster (matches `USE_MOCK_INFERENCE=true` being the whole reason a Mock
Adapter exists for Golden Path #2's serving side). A `ClusterComponentType`
wrapping KServe genuinely has nothing to wrap yet; writing one now would
be unverifiable YAML, not a real capability. The dependency order is:

1. Install KServe on `openchoreo-quick-start` (or a DataPlane pointed at a
   cluster that already has it).
2. Only then design the `ClusterComponentType` — its `resources[].template`
   is OpenChoreo's own CEL-templated resource-generation DSL (see
   `platform/component-orchestration-api.yaml`'s sibling `service`
   ClusterComponentType, read via
   `kubectl get clustercomponenttype service -o yaml`, for the shape) —
   sketching it against a KServe install that doesn't exist risks
   producing something that looks plausible but was never actually
   validated, which is worse than not having it.

## Workflow wrapping Golden Path #1's training: achievable, not started

Unlike the above 2, this one has no missing infrastructure —
`kubectl get clusterworkflowplanes` shows a real `default`
`ClusterWorkflowPlane` already running (it backs the 4 buildpack
`ClusterWorkflow`s used for container-image builds). Wrapping
`infra/argo-workflows/train-register-template.yaml`'s logic as a
`Workflow`/`ClusterWorkflow` CR is real, scoped work — just not attempted
in this pass; `platform/`'s own 2.1 work (getting `orchestration-api`
itself running as a Component, plus 2 unrelated live infra incidents —
a Docker daemon hang and this control plane's own reconciler getting
stuck twice, both documented in `infra/openchoreo/README.md`) used up the
session's remaining budget first.
